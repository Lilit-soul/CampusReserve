# Contributing

Этот файл описывает желаемые правила работы с репозиторием. Прошу вас всех их соблюдать дабы не быть огретым тежелым предметом из за того что репо засрется.

---

## Ветки
| Наименование | Назначение |
|--------------|------------|
| `main` | Версия готового продукта. Только через PR и только из `dev` |
| `dev` | Основная ветка. Все лить сюда |
| `feat/*` | Фича, новая функция |
| `chore/*` | Рефакторинг, изменения без чего то нового |
| `fix/*` | Исправления |
| `docs/*` | Документация |
> Примечание: "\*" в таблице выше, обозначает любое слово (или словосочетание с "-" вместо пробела)

### Некоторые правила

 - Прямой push в `main` и `dev` **Запрещен** — только через PR (Pull Request)
 - Все новые ветки создаются от `dev`
 - После выполненого слияния удалить feat ветку

```bash
#Начало работы над задачей
git checkout dev
git pull origin dev
git checkout -b feat/название-задачи
```

## Коммиты
 
Используем [Conventional Commits v1.0.0-beta4](https://www.conventionalcommits.org/ru/v1.0.0-beta.4/):
 
```
<тип>[контекст]: <краткое описание>
```

Так как наш состав небольшой предлогаю использовать блок [контекст] для нужных флагов помогающих понимать некоторый дополнительный контекст коммита

**Флаги**:
| Флаг | Описание | Что будет значить |
|------|----------|-------------------|
| `[WIP]` | Work in progress | Коммиты(или PR) с данным флагом не будут рассматриваться как готовая работа (в случае с PR автоматически отправляется в draff) (Так же не рекомендуются отправлять коммиты с этим флагом на ветку, использовать локально) |
| `[NOCI]` | No Continuous Integration | Коммиты(или PR) с данным флагом не будут вызывать автоматическую проверку и пересборку проекта |

**Типы**:
| Тип | Когда использовать |
|-----|-------------------|
| `feat` | Новый функционал |
| `fix` | Исправление бага |
| `docs` | Изменения в документации |
| `test` | Добавление или исправление тестов |
| `ci` | Изменения в CI/CD |
 
**Примеры**:
 
```
feat: добавить авторизацию через JWT
fix: исправить ошибку 500 при создании пользователя
docs: обновить README с инструкцией по запуску
feat[WIP]: составил коркас функции формирования нужных документов
```

## Pull Requests
 
1. Создай PR в `dev` (или в `main` если это релиз из `dev`)
2. Заполни шаблон PR — название, описание, ссылка на Issue
3. Дождись прохождения CI
4. Попроси ревью если нужно (для `main` аппрув обязателен)
 
### Название PR
 
Такой же формат как у коммитов:
 
```
feat: добавить страницу профиля пользователя
fix: исправить баг с авторизацией на мобильных
```
 
### Размер PR

Старайся делать небольшие PR — до 400 строк изменений. Большие сложно ревьюить.
